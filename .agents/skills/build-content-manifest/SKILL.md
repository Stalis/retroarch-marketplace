# Build a content manifest

Use this skill when a user wants an agent to create or extend this project's `catalog-source.json` (or another source manifest) from their local content. The goal is a domain manifest for this server, not a RetroArch playlist, ZIP archive, or `/api/games` response.

## Discover and plan

1. Read the current `README.md`, `internal/content/content.go`, and `web/src/platforms.js` for the current schema, validation, and built-in platform names. Inspect the existing manifest if the user wants to extend one; preserve its games, platforms, and user changes. Confirm the destination and content roots from the request or project configuration. If they cannot be determined, ask. Never overwrite an existing manifest without the user's permission.
2. Inspect only the content roots authorized by the user. A root may be a symlink; inspect its target without modifying it. Identify each game's files, disc entrypoints, and any existing CUE/M3U references. Do not recursively scan unrelated directories or include BIOS, archives, manuals, or unrelated files unless the user explicitly requests them and the game requires them. Do not download or distribute game data.
3. Verify facts from the files. Do not invent CUE files, entrypoints, disc order, game titles, or platform assignments. Ask when they cannot be established reliably. Preserve existing CUE bytes and ensure each `FILE` reference resolves to the exact corresponding package path, including case. Relative M3U references and CUE paths must resolve inside the package. The server generates a playlist when `playlist` is specified; for multiple discs use the verified disc order. Never list the generated playlist among a disc's source files.
4. Choose safe unique game and platform IDs. Reuse matching existing platforms; otherwise use the exact `libretro_name` from `web/src/platforms.js` where applicable. A custom platform is allowed when the user provides or confirms the values. Platform presets are not automatically inserted into the manifest.
5. For each game being added, use the `find-canonical-name` skill after identifying its files and platform. From the project root, its lookup runs `go run ./cmd/find-canonical-name -platform '<exact libretro_name>' -q '<game title>'`. Treat results as suggestions and compare release evidence; ask when identity is ambiguous, and never silently substitute an unrelated suggestion. If the lookup fails or returns no candidates, a title verified from the user's files or confirmed by the user may still be used. Preserve existing games' canonical names unless the user explicitly requests changes.

## Manifest rules

The top level is an object with `platforms` and `contents` arrays. Each platform has `id`, `name`, and `libretro_name`. Each content item has `id`, `canonical_name`, optional `display_name`, `platform_id`, and a nonempty ordered `discs` array. Each disc has an `entrypoint` and a nonempty `files` array of `{ "source": "...", "path": "..." }`. For multiple discs set `playlist` to a unique package-relative path; it is optional for one disc. Consult the README for an example.

`source` is relative to the directory containing the manifest, not the current shell directory. `path`, each disc `entrypoint`, and `playlist` are relative to the package root. Paths use `/`, are nonempty, and cannot contain empty, `.` or `..` components, backslashes, colons, or control bytes. IDs and `libretro_name` are single safe components; all required strings and present optional strings must be nonempty and contain no NUL. IDs must be unique; package file paths must be unique within a game; each disc entrypoint must exactly match one of that disc's file paths. The generated playlist must not collide with a file. Verify references relative to the containing CUE or generated playlist, not the manifest directory.

Source paths cannot escape the manifest directory with `..` or be absolute. If the files are outside it, choose a suitable manifest location or ask the user before creating a symlink inside that directory. Never alter or delete originals, including symlink targets. If an existing CUE names a file with different case, the package `path` may use the name required by the CUE while `source` retains the real original name; verify every reference rather than renaming the source.

Do not silently use `defer_missing`: if sources are missing, show the exact paths and ask whether to leave the game out or explicitly save it as deferred. With explicit approval, `"defer_missing": true` on that game allows missing files; the game is hidden from downloads until all files exist. It does not waive invalid paths, missing entrypoint membership, non-regular files, or permission errors.

## Write and verify

1. Prepare a candidate file in the **same directory** as the destination, so relative source paths resolve exactly as they will after publication. Preserve the existing manifest when extending it. Do not create ZIPs; downloads build them lazily.
2. Validate the candidate using the actual server before publishing: start `go run .` from the project root with `-config config.example.toml`, `-catalog` pointing to the candidate, `-packages` pointing to a new temporary directory, and `-listen` set to an available loopback port. Wait for `GET /api/games` to succeed, inspect the returned cards and entrypoints, then stop the server and remove only the temporary cache. Treat a startup error or unexpected catalog as a failed validation. Deferred games are intentionally absent from the response until their files appear. Use a fresh temporary cache so validation cannot remove or reuse the user's cache.
3. For a representative available game, request the `download_url` resolved relative to `/api/games` and inspect the ZIP against the card's `files`; verify the entrypoint and internal CUE/M3U links and report any uncertainty. The test creates an archive only in the temporary cache. Do not launch RetroArch unless the user asks and a client is available.
4. Publish only after validation, using an atomic replacement in the destination directory and the user's permission if replacing an existing file. Do not replace a symlink or overwrite unrelated files. Clean up only files created for this task. Report the manifest path, platforms, games, deferred or excluded items, and checks actually performed. Tell the user how to start the server with `-catalog <path>`.
